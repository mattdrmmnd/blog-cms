## Project

A personal blog ("Matt The Dev") with a public frontend and an admin CMS, built to learn the full web stack. It uses Vite + Tailwind CSS v4 and was designed in Figma. The site now lives in `C:\xampp\htdocs\blog-cms` and Apache serves it at http://localhost/blog-cms/. **Every page is now a `.php` file built from the shared `includes/`.** The **MySQL backend has started**. Blog posts have started: the `blog_posts` table, the admin list, trash, restore, permanent delete, and one merged form that creates and edits posts as a draft or published (with a session keep-alive while typing) and keeps, replaces or removes the featured image (see "Blog posts" below). Everything else (reading posts, users, requests, settings) is still a mockup with hardcoded content. A full REST API isn't planned, because the pages are server-rendered. The README tracks progress.

## Commands

- `npm run build`: runs `tsc` (type-checks `src/` only) and then `vite build`, which compiles `src/` into `build/main.css` and `build/main.js`. Use it for a one-off build and to catch type errors before committing.
- `npm run watch`: `vite build --watch`. It rebuilds `build/` on every save in `src/`, but skips `tsc`. The user runs it while working, then reloads the page in Apache.
- `npm run dev`: Vite dev server at http://localhost:5173. It can't run PHP, so it's no longer useful for this site. Test in Apache instead.
- `npm run preview`: left over from the old `dist/` setup, not useful now.

`build/` is gitignored, so a fresh clone needs `npm install` and then `npm run build` before the PHP pages have any CSS or JS. There are no tests and no linter.

## Architecture

- **Multi-page site, no framework or router.**
  - Every page shares its head, header, sidebar and footer through `includes/`, so a shared markup change, like a sidebar link, is made once in the include.
  - Public pages are in the root: `index.php`, `post_writing.php`, `post_previews_*.php`. `writing.html` is a leftover stub. `about.html` is obsolete because its content moved to the home page, so it was never converted. Don't fix or update it.
  - Admin pages are in `admin/`.
- **`includes/`:**
  - `config.php` defines `BASE_URL` (`/blog-cms/`). Build every link and asset path from it (`<?= BASE_URL ?>public/images/…`) so it works from any folder, including `admin/`. If the site moves to another folder or the server root, change it only here.
  - `head.php` opens the page: doctype, `<head>`, the Instrument Sans and Material Symbols Google Fonts, `build/main.css`, `build/main.js` and `<body>`. Set `$pageTitle` and `$bodyClass` before requiring it. It also resumes the session, but only when the browser already has a session cookie, so ordinary visitors get no cookie. Material Symbols only downloads the icons listed in `icon_names=` in its URL, so new icons must be added there (comma-separated, alphabetical) or they show as plain text.
  - `header.php` is the public header and nav. When logged in it shows a Dashboard link and a "Logout, <username>" button instead of Login. A public page sets `$activePage` (`'writing'` or `'reading'`) to highlight its nav link: the link gets `aria-current`, styled by `aria-[current]:text-orange-200`. The value comes from `$ariaCurrent ?? 'page'`. The single post page sets `$ariaCurrent = 'true'` with `$activePage = 'writing'`, because the link points to the list, not the page being read. The home page sets neither, so neither link is highlighted. The two list pages have an `sr-only` `<h1>`, since the highlighted nav already shows sighted users where they are. `footer.php` is the footer (with `<?= date('Y') ?>`) and closes `</body></html>`, so any page `<script>` goes before it (see `post_writing.php`).
  - `admin_header.php` is the logged-in admin header (logo, a Home link to the public site, and "Logout, <username>"). `admin_sidebar.php` is the admin nav. Set `$activePage` to the current section's key (`dashboard`, `posts_blog`, `posts_reading`, `users`, `requests`, `settings`) to highlight its link. `admin/featured_posts.php` (the old three-slot featured posts mockup) is no longer linked from the sidebar; it's kept for a possible later version of the idea. Sub-pages use their parent's key, e.g. `users_add_new.php` uses `users`.
  - `auth_header.php` is the header for the logged-out pages (`login.php`, `request_access.php`). Set `$headerMessage` to the note shown top right.
  - Page pattern: set the variables, `require __DIR__ . '/includes/head.php'`, the page content with the header (and sidebar) includes, and `require …/footer.php` last. Admin pages use `__DIR__ . '/../includes/…'` and require `auth.inc.php` before `head.php`. See `index.php` and `admin/users.php`.
  - Always start include paths with `__DIR__`. A bare relative path like `'includes/config.php'` resolves from the page the browser opened, not from the file that contains the `require`.
- **[vite.config.ts](vite.config.ts)** has two modes:
  - **Build** (`build`/`watch`), the one that matters: the only input is `src/main.ts`. Output goes to `build/` with fixed names (`main.js`, `main.css`, no hashes), so PHP can link them directly. `base` is `/blog-cms/build/` so asset URLs inside the CSS resolve, and `publicDir` is off because PHP links `public/` directly. `emptyOutDir: true` wipes `build/` on every build, so never put anything else in it.
  - **Dev** (`npm run dev`): normal Vite serving, left over from the `.html` mockups. Only `about.html` and `writing.html` remain for it to serve.
- **[src/main.ts](src/main.ts) is the only entry point**, and every page loads it through `build/main.js` in `head.php`. It imports the CSS and holds small shared behavior. Right now that's closing an open `details.dropdown` menu when the user clicks outside it, the show/hide password toggle: a `<button type="button" data-password-toggle aria-controls="<input id>">` placed next to a password input, and a confirm step: clicking any element with `data-confirm="<message>"` shows `confirm(message)` and cancels the click if the user says no. It uses one page-wide click listener, so it covers rows added later too. The Delete button in the blog trash view uses it. Last is `keepAlive()`, the session keep-alive described under "Blog posts".
  - New JS goes in `main.ts` or in a new `src/*.ts` file imported from it, so it lands in the single bundle with no new `<script>` tags. Page-specific code should check for its elements first and do nothing when they're missing.
- **[src/style.css](src/style.css)** is the Tailwind v4 entry point:
  - Tailwind scans the project, `.php` files included, for classes. `@source "../admin"` adds the admin pages explicitly.
  - New CSS goes here, or in a new file `@import`ed right after `@import "tailwindcss"`.
  - The `@theme` block defines the custom tokens used throughout the markup: the colors `xlight-purple`, `light-purple`, `dark-purple`, `darkest-purple`, and `mango`; the `font-instrument` font (Instrument Sans, set on `<body>` through `$bodyClass` on every page); the `bg-check` check-mark image used by checked checkboxes and radios (`checked:bg-check`); and the extra breakpoints `xmid`, `mid`, `mid1000`, and `footer` (910px, where the footer switches from stacked to its three-column row, set by the width of the social links).
  - Images used from CSS must be theme tokens pointing at `../public/images/…`, like `--background-image-check`, so Vite rewrites the URL during a build (it copies large files into `build/` and inlines small ones). An arbitrary class like `bg-[url('/images/…')]` breaks under Apache.
  - It also defines the `.button` component, the `grid-cols-autofit` utility, and the plain-CSS Category dropdown.
- **Category dropdown pattern:** `<details class="dropdown">`, with `<summary class="dropdown-button">` as the toggle and `.dropdown-menu` holding checkboxes named `items[]`. The checkbox values are still placeholders (`item1`…`item10`). Only `posts_reading_new.php` uses it now. It was removed from the blog form until categories exist, and the CSS stays for later.
- **Static assets** live in `public/` (`public/images/`, favicons). Every page links them as `<?= BASE_URL ?>public/…`.

## Login and sessions

- **Database:** MySQL database `dynamicblog` with three tables so far (`blog_posts` is described under "Blog posts"). **`database_schema.sql`** in the root is a phpMyAdmin structure-only export, with no data, no password hashes and no `CREATE DATABASE`. Re-export it whenever a table changes, so it stays current.
  - `users`: `id`, `username` (unique, the login name, never shown publicly), `display_name` (`VARCHAR(100) NULL`, the name in public bylines, e.g. "Matt D"), `pwd` (`password_hash()` output, `VARCHAR(255)`), `email` (unique), `created_at` (defaults to `CURRENT_TIMESTAMP`). There's no signup; the admin user was inserted by hand with a hash made by `password_hash()`.
  - `login_attempts`: `id`, `ip` (`VARCHAR(45)`), `username`, `attempted_at` (defaults to `CURRENT_TIMESTAMP`), with an index on `(ip, username, attempted_at)`. One row per failed login.
- **`includes/dbh.inc.php`** connects with PDO (`utf8mb4`, exceptions on, `FETCH_ASSOC` by default) and creates `$pdo`. It holds the credentials, so it's **gitignored**. `dbh.inc.example.php` is the committed copy with blank values.
- **Login** follows a tutorial-style MVC split:
  - `admin/login.php` is the form. It logs in by **username**, with fields `username`, `pwd` and the `remember` checkbox, and posts to `includes/login.inc.php`. It redirects to the dashboard if already logged in.
  - `login.inc.php` is the handler, in this order:
    1. POST only, then the CSRF check.
    2. The empty-field check.
    3. **The lockout check:** 5 or more failed attempts from this IP for this username in the last 15 minutes redirects with "Too many login attempts" before the password is checked.
    4. The credential checks.
    5. On failure, it records an attempt (wrong credentials only), sets `$_SESSION["errors_login"]` and redirects back.
    6. On success, it clears this IP's attempts, regenerates the session ID and the CSRF token, and sets `user_id`, `user_username`, `last_regeneration`, `login_time`, `last_activity` and `remember`.
  - The lockout counts per IP and username together, so someone who knows the username can't lock the real user out from another IP. Old rows aren't deleted on a timer; they just stop counting once they're older than 15 minutes, and a successful login deletes them. Times come from MySQL (`NOW()`, `CURRENT_TIMESTAMP`), never PHP's `time()`, so the two clocks can't disagree.
  - `login_model.inc.php` holds the prepared-statement queries (`get_user()`, `recent_attempts()`, `failed_attempt()`, `clear_attempts()`), `login_contr.inc.php` the checks, and `login_view.inc.php` the output (`check_login_errors()`, `output_username()`).
  - Both credential failures show the same "Incorrect login info." message on purpose.
- **`includes/config.session.inc.php`** is loaded on every page that has a session. In order, it:
  1. Sets strict, cookie-only sessions with `samesite Lax`, `secure` and `httponly` cookies.
  2. Sets `gc_maxlifetime` to 4 hours.
  3. Starts the session.
  4. Regenerates the ID every 30 minutes.
  5. Checks the timeout: if `last_activity` is older than the limit, it calls `session_unset()`. The limit is 4 hours with `remember`, 30 minutes without. Both are **inactivity** timers, not a fixed cap.
  6. Creates the CSRF token if it's missing. This must stay after the timeout check, which wipes it.
  7. Re-sends the cookie with a 4-hour expiry when `remember` is set.
- **`includes/auth.inc.php`** is the auth guard. It redirects to the login page unless `$_SESSION["user_id"]` is set. Every admin page except `login.php` and `request_access.php` requires it before `head.php`.
- **`admin/logout.php`** is POST only with a CSRF check. It clears the session, deletes the cookie, destroys the session and redirects to login. Any other request just redirects.
- **`includes/csrf.inc.php`** (loaded by `config.session.inc.php`) has three functions:
  - `csrf_field()` prints the hidden token input. Put it in every POST form.
  - `csrf_verify()` stops with a 403 on a bad token. Call it at the top of every POST handler.
  - `csrf_is_valid()` returns true or false. `login.inc.php` uses it so it can redirect back with a message instead.
- Always follow `header('Location: …')` with `die()` or `exit`.

## Blog posts

- **`blog_posts` table:** `id`, `title` (`VARCHAR(255)`), `body` (`TEXT`), `featured_image` (file name only), `featured_image_alt`, `featured_image_caption` (all three `VARCHAR(255) NULL`), `status` (`ENUM('draft','published')`, default `'draft'`), `published_at` (`DATETIME NULL`, set the first time a post is published and kept after that, so unpublishing and republishing keeps the date; drafts that were never published are `NULL`), `pinned_at` (`DATETIME NULL`, the date the post was pinned to the top of Recent Posts; at most one post has it), `trashed_at` (`DATETIME NULL`), `created_at`, `updated_at` (`ON UPDATE CURRENT_TIMESTAMP`), `user_id` (foreign key to `users.id`, `ON DELETE SET NULL`). There are no categories yet; they come later as their own tables.
- **Trash is a soft delete.** `trashed_at` is `NULL` for a live post and holds a date once trashed. Restore sets it back to `NULL`, so the post keeps its draft/published status. A permanent `DELETE` only matches posts that are already trashed (`AND trashed_at IS NOT NULL`), so a forged id can't delete a live post. Every query that lists posts must filter on `trashed_at`, and the public pages also on `status = 'published'`.
- **`includes/posts_model.inc.php`** holds the queries:
  - `get_blog_posts($pdo, bool $trashed = false)` uses a `LEFT JOIN` to `users` for the author's `display_name`, which is `NULL` if the user was deleted or has no display name set (the list prints "Unknown" then). It also selects `pinned_at` for the Pin/Unpin label.
  - `trash_blog_post()`, `restore_blog_post()` and `delete_blog_post()` are prepared statements with `PDO::PARAM_INT` that return `rowCount()`. Trash also clears the pin (`SET trashed_at = NOW(), pinned_at = NULL`), so a restored post comes back unpinned.
  - `pin_blog_post($pdo, int $id): int` uses a **transaction**: `beginTransaction()`, clear every pin, then pin this post `WHERE id = :id AND status = 'published' AND trashed_at IS NULL`. If that `rowCount()` is 1 it calls `commit()`, otherwise `rollBack()`, which brings the old pin back. So only one post is ever pinned, and a failed pin (a draft, a trashed post or a forged id) changes nothing. Both paths reach one `return`. `unpin_blog_post($pdo, int $id): int` is one `UPDATE … SET pinned_at = NULL WHERE id = :id AND pinned_at IS NOT NULL` with no transaction.
  - `get_recent_posts($pdo): array` returns `id`, `title`, `published_at` and `pinned_at` of the 5 newest published, untrashed posts, with the pinned one first: `ORDER BY pinned_at IS NULL, published_at DESC` (`pinned_at IS NULL` is 0 for the pinned post and 1 for the rest). It has no parameters, so it uses `query()`.
  - `get_blog_post($pdo, int $id): ?array` returns one **untrashed** post (`id`, `title`, `body`, `status` and the three image columns) with `fetch()`, or `null` (`$post ?: null`, because `fetch()` returns `false` when there's no row).
  - `create_blog_post($pdo, int $userId, string $title, string $body, string $status, ?string $featured_image, ?string $featured_image_alt, ?string $featured_image_caption): int` inserts a post and returns the new id from `lastInsertId()`. It sets `published_at` to `NOW()` when `$status` is `'published'` and `NULL` otherwise, through `$publishedAt`, a fixed SQL snippet put straight into `VALUES` (a bound value is always data, so binding `'NOW()'` would store the text). The three image values are nullable and are `NULL` when there's no image.
  - `update_blog_post($pdo, int $id, string $title, string $body, string $status, ?string $featured_image, ?string $featured_image_alt, ?string $featured_image_caption): void` updates an untrashed post (`WHERE id = :id AND trashed_at IS NULL`). It returns nothing, because MySQL's `rowCount()` is 0 when nothing changed, so it can't tell "saved" from "not found". When `$status` is `'published'`, `$publishedAt` adds `, published_at = COALESCE(published_at, NOW())` to the `SET` list (`COALESCE` returns its first non-`NULL` value, so an existing date is kept); otherwise it adds nothing and the column is left alone. The parameters are in the same order as `create_blog_post()`. PHP matches arguments by position, so check the order at each call.
  - `get_blog_post_image($pdo, int $id): ?string` returns a **trashed** post's `featured_image` with `fetchColumn()`, or `null`. The delete handler calls it before the `DELETE`, while the row still exists.
  - **Public queries:** `get_published_post($pdo, int $id): ?array` returns one post (`id`, `title`, `body`, `published_at`, the three image columns and `users.display_name` through a `LEFT JOIN`) only when it's published and untrashed, or `null`. `get_published_posts($pdo): array` returns `id`, `title`, `body` and `published_at` of every published, untrashed post, newest first by `published_at` (no author or image columns, because the list doesn't show them; add the image columns back if the list gets images). `get_more_posts($pdo, int $id): array` returns `id`, `title` and `published_at` of the 4 newest published, untrashed posts other than `$id` (`id != :id … LIMIT 4`); `fetchAll()` gives `[]` when there are none. Never use `get_blog_post()` on a public page: it returns drafts.
- **`admin/posts_blog_form.php`** is one form for new and edit posts. With no `?id` it creates a post. With `?id=N` it edits that post.
  - **Loading (before the POST block):** `$isEdit = isset($_GET["id"])`. When editing, the id goes through `filter_input(INPUT_GET, "id", FILTER_VALIDATE_INT)` and `get_blog_post()`, and a bad, missing or trashed id stops with `http_response_code(404)` and `die()`. It then sets `$isPublished` (the status **before** this save), `$currentImage`, the Edit page title, `$formAction` with `?id=` added, and fills the fields from `$post`. The id always comes from the URL that was checked, never a hidden form field.
  - **Markup that switches on edit:** the heading (`Edit`/`New`), the form action, and the button labels: a published post shows Unpublish / Update, otherwise Save draft / Publish. Only the labels change. The `value`s stay `draft` and `published`.
  - It handles its own POST before `head.php` (Post/Redirect/Get):
    1. If `$_POST === []`, the request was over `post_max_size` and PHP threw the whole form away, so it only adds a "too large" error. This branch comes before `csrf_verify()`, which would otherwise stop with a 403.
    2. Otherwise `csrf_verify()`, then `trim()` the title, body, alt text and caption.
    3. `status` comes from the clicked button (`name="status"`, `draft` or `published`) and is checked with `in_array(…, true)`, falling back to `'draft'`.
    4. Validation fills `$errors`: the title is required (max 255 with `mb_strlen()`), the body is required only when publishing, and the alt text and caption are max 255 each.
    5. The image (see "Featured images" below) adds its own errors, and sets `$hasImage`, `$removeImage` and `$willHaveImage`.
    6. With no errors, it moves the new image (if any). A second `if (!$errors)` catches a failed move. Then it saves: `update_blog_post()` when editing, or `create_blog_post()` with the session's `user_id` (never a form field). `$postId` is `$id` or the new id.
    7. The flash message is an `if`/`elseif` chain, most specific first: was published + `draft` = "Post unpublished.", was published + `published` = "Post updated.", `published` = "Post published.", otherwise "Draft saved.".
    8. The redirect: `draft` goes to `posts_blog_form.php?id=$postId`, so writing can continue and a second Save draft updates the same post instead of creating a duplicate. `published` goes to the list. One `die()` follows both.
    9. With errors, it falls through and redraws the form: the error list (`role="alert"`) in the top row, and the text fields filled back in with `htmlspecialchars()`. The `<textarea>` content must sit right between its tags with no whitespace. Browsers never refill a file input, so a new image has to be chosen again.
  - The flash message prints in the form's top row, in the same spot as the errors (they never show together: the flash comes after a redirect, the errors after a failed save).
- **Featured images:**
  - Uploads go in `public/uploads/blog/`. The images in it are gitignored, but its `.htaccess` is committed, which keeps the folder in the repo. The `.htaccess` is an allowlist: `Require all denied`, then only `.jpg`/`.jpeg`/`.png`/`.webp` are granted, and `Options -Indexes` hides the file list. So nothing in the folder can run as PHP.
  - `$_FILES["featured_image"]["error"]` is checked first with the `UPLOAD_ERR_*` constants: `NO_FILE` is fine (images are optional), `INI_SIZE` means over php.ini's `upload_max_filesize`, and any other non-`OK` code is a failed upload. `$hasImage` is `true` only for `UPLOAD_ERR_OK`.
  - Inside `if ($hasImage)`: the real type comes from `new finfo(FILEINFO_MIME_TYPE)->file($image["tmp_name"])`, never the browser's `type` or the file name, and must be a key in `$imageTypes` (`image/jpeg` → `jpg`, `image/png` → `png`, `image/webp` → `webp`). The same map gives the saved extension. The page's own 2 MB limit checks `$image["size"]`, because a host's php.ini may allow more. The alt text check sits outside this block and uses `$willHaveImage` (see "Editing the image").
  - Saving: the name is `bin2hex(random_bytes(16))` plus the extension, and `move_uploaded_file()` puts it in `$uploadDir` (`__DIR__ . '/../public/uploads/blog/'`, a disk path, not `BASE_URL`, which is only for `<img src>`). PHP deletes the temporary file when the request ends, so the move must happen in the same request.
  - **Editing the image:** when the post has one, the form shows a "Current image" preview and a "Remove image" checkbox (`name="remove_image"`).
    - `$removeImage = isset($_POST["remove_image"]) && $currentImage && !$hasImage`. A new upload beats Remove, so the two are never both true and the rest of the code can trust that.
    - `$willHaveImage = $hasImage || ($currentImage && !$removeImage)`. Alt text is required when it's true, so a kept image still needs its alt text and a removed one doesn't.
    - `$imageToSave = $hasImage ? $fileName : ($removeImage ? null : $currentImage)`: the new file, `NULL`, or the current file. PHP 8 needs the parentheses around a nested ternary.
    - The order is move, then `UPDATE`, then delete. After the update, `if (($hasImage || $removeImage) && $currentImage)` deletes the old file with `is_file()` and `unlink()`, so a failed upload or validation error never loses the old image.
  - The database gets the file name, the alt text only when there's an image, and the caption only when there's an image and it isn't empty (`$altToSave`, `$captionToSave`, both based on `$willHaveImage`). Otherwise those columns are `NULL`.
  - XAMPP's php.ini has `upload_max_filesize = 2M` and `post_max_size = 8M`, and `display_errors = Off`, so PHP errors only show in `C:\xampp\apache\logs\error.log`. Check there when a page goes blank.
  - Known gaps: if the insert or update fails after the move, the new file stays in the folder with no post pointing at it. When the form is redrawn with errors, the Remove image checkbox isn't ticked again.
- **Session keep-alive:** typing doesn't count as activity, so a long writing session could time out and lose the post on save.
  - `admin/ping.php` loads `config.php` and `config.session.inc.php` (which refreshes `last_activity`) and returns `204`, or `401` when not logged in. It doesn't use `auth.inc.php`, because `fetch()` would quietly follow its redirect.
  - The blog form has `data-keep-alive="<message>"`. `keepAlive()` in `main.ts` sets a flag on the form's `input` event, and every 5 minutes pings `ping.php` only if the flag is set, then clears it. So typing keeps the session alive, and an open but idle tab still times out normally. On a `401` it alerts the attribute's message.
  - To test, set `$idleLimit` to `60` and the interval to 20 seconds, log in without "Keep me logged in", and filter the Firefox Network tab for `ping`. Set both back afterwards.
- **`admin/posts_blog.php`** lists live posts. With `?view=trash` it lists the trash instead. The All posts / Trashed links mark the current view with `aria-current="page"`, which also styles it through `aria-[current=page]:` classes. The New post link goes to `posts_blog_form.php`. The live rows have Edit (`posts_blog_form.php?id=N`) and Trash, published live rows also have Pin or Unpin, and the trash rows have Restore and Delete. Each action is a POST form with `csrf_field()` and a hidden `id`. The Pin form also has a hidden `action` (`unpin` when `$post["pinned_at"]` is set, `pin` otherwise; a truthy check, because the column is a date string or `NULL`, never `1`), and its label and `aria-label` switch the same way.
- **Handlers:** `admin/posts_blog_trash.php`, `posts_blog_restore.php` and `posts_blog_delete.php` all share one shape:
  1. The auth guard, POST only, then `csrf_verify()`.
  2. `filter_input(…, FILTER_VALIDATE_INT)` with a guard clause.
  3. The model call.
  4. They set `$_SESSION["posts_message"]` from the row count and redirect back. Trash returns to the list, and Restore and Delete return to `?view=trash`.
  - Delete also removes the image: it reads the name with `get_blog_post_image()` before the `DELETE`, and after it, only if `$deleted === 1` and there was an image, calls `unlink()` when `is_file()` finds the file.
  - `admin/posts_blog_pin.php` has the same shape plus a second guard: `$action = $_POST["action"] ?? ''` must pass `in_array($action, ['pin', 'unpin'], true)`. Both branches store the count in `$changed`. The flash is an `if`/`elseif` chain: "Post pinned.", "Post unpinned.", "Only published posts can be pinned." (pin, 0), else "Post not found.". It returns to the list.
- **Flash message:** `posts_blog.php` and `posts_blog_form.php` both print `$_SESSION["posts_message"]` in a `role="status"` paragraph and then unset it, so it shows once on whichever page loads next.

## When deploying to production

When the user says they're ready to put the site on a remote host (e.g. Bluehost), remind them of this checklist:

- **Paths:** `BASE_URL` in `includes/config.php` and `base: '/blog-cms/build/'` in `vite.config.ts` both assume the site is at `/blog-cms/`. At the domain root they become `/` and `/build/`. Change both, then run `npm run build`, because the base is baked into `build/main.css`. Offer to make them switch automatically between localhost and production.
- **What to upload:** the root `.php` pages, `admin/`, `includes/`, `public/` and `build/`. Leave out `node_modules/`, `src/`, `package.json`, `package-lock.json`, `vite.config.ts`, `tsconfig.json`, `.git/`, `.claude/`, `CLAUDE.md`, `README.md`, `database_schema.sql`, `about.html` and `writing.html`. With cPanel Git deployment, `build/` still needs a separate upload because it's gitignored.
- **Server setup:** pick a PHP version in cPanel that matches or is newer than XAMPP's. Create the MySQL database and user, and import the tables with phpMyAdmin. The database name will likely get a cPanel account prefix. `includes/dbh.inc.php` is gitignored, so create it on the server from `dbh.inc.example.php` with the production credentials. Turn on SSL and redirect to `https`, which the `secure` session cookie requires. Turn `display_errors` off and log errors instead.
- **Linux differences:** file names are case-sensitive. Block direct access to `includes/` (with `.htaccess`, or move it above `public_html`). Make `public/uploads/blog/` writable, and check its `.htaccess` was uploaded (dot files are easy to miss). Uploaded images aren't in git, so copy them across separately. If the host's PHP is older than 8.4, `new finfo(…)->file(…)` needs brackets: `(new finfo(…))->file(…)`.
- **Admin:** sessions, login, the auth guard, CSRF and login attempt limiting exist now. Before deploying `admin/`, also have https, blocked access to `includes/`, and the password handling above. Import all the tables (`users`, `login_attempts` and `blog_posts`) from `database_schema.sql`. Until then, deploy only the public pages.
